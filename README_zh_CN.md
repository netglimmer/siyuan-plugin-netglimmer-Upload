# Netglimmer 上传（siyuan-plugin-netglimmer-Upload）

一键把文档按 **HTML (SiYuan) / Markdown / Word (.docx)** 三种导出格式之一**上传**到 WebDAV / FTP / SFTP 服务器或本地目录（回归里真跑过的是 IIS WebDAV、IIS FTP、Nginx dav、vsftpd、OpenSSH-SFTP；群晖 / 威联通 / Alist 这类只要实现标准协议就能用，但本机没有真机，不在「已实测」之列）。选 HTML (SiYuan) 时，上传出来的页面与官方「文档分享」渲染效果一致：双链、块引用、块嵌入、图片资产全部保留。

> **这个插件只做「把文件传到服务器上」这一件事。** 它不部署站点、不管端口、不发证书——那个目录能不能用浏览器打开、以什么域名打开，是服务器（IIS / nginx / 别名映射 / 挂载点）的决定，插件既不知道也猜不准。所以界面上只说「上传」，不说「发布」；按钮只给「查看上传路径」，不承诺「打开 / 复制访问地址」：把文件真正落在了哪个目录摊开给你看，剩下的路你自己走。

## 它解决什么问题

手动「导出 HTML → 复制到网站目录」的两个痛点：

1. 每次改完都要重新导出、挑文件、复制；
2. 目录命名混乱，重复上传留下旧文件。

本插件把整条链路自动化：右键 → 按当前设定的导出格式导出到思源临时目录 → 多路并发上传到服务器 → 读回校验 → 清理临时文件。重复上传同一文档时默认走增量：思源运行时（HTML 档每次导出都附带的那约 570 个逐字节相同的文件）已在服务器上就跳过重传，只传本文自有内容和有变化的文件，传完再清掉本目录里不再需要的旧资产。Markdown 与 Word 两档没有这套运行时可复用，每次传出去的就是正文加它真正引用到的那几个文件。

> 注：HTML 档里，思源 3.8.6 的内核导出接口不写 index.html（由前端拼装后经单独的落盘接口写出）。本插件内置了与前端逐字一致的拼装代码，上传时自行生成并写出 index.html，内容与手动导出的「HTML (SiYuan)」逐字节一致。Markdown 与 Word 两档不需要这条：内核的导出接口直接给出成品（一个是 `.md` 正文，一个是 pandoc 排好的 `.docx`），插件原样上传，不改一个字节。

## 安装

解压到 `{工作空间}/data/plugins/siyuan-plugin-netglimmer-Upload/`，重启思源。仅支持桌面端。

> 设置与上传历史只读写当前标识 `siyuan-plugin-netglimmer-Upload` 自己的 `settings.json` / `history.json`：**不读别的插件的存储，也不替任何别处的配置做形状转换**。这个标识下没有数据，就是一份空设置加空历史——第一次上传时把服务器/账号填一遍即可。

## 配置

入口：思源「设置 → 插件市场/已加载插件 → Netglimmer 上传」的原生插件设置面板（未配置就点上传时会自动打开该面板）。

> **推荐组合：WebDAV + HTML (SiYuan)**——这一条不只写在下面两张表里，插件设置页的**最上方**（第一条设置项之前）就钉着它，理由与本文一致：HTML (SiYuan) 是三档里唯一「一整页」的格式，明暗主题、代码高亮、侧边大纲、图片点击放大、双链与块嵌入都在，离线打开也是完整一页，还原度与风格完整性最高；WebDAV 走的是普通 HTTP（`PUT`/`DELETE`/`MKCOL`/`PROPFIND`），浏览器、代理、防火墙都不额外挑，本套件的端到端回归也在它上面跑得最足（真实 IIS 与 nginx 各一遍，逐字节读回校验）。另两档各有取舍：Markdown 只有正文加它真正引用到的图，不带运行时、不注入大纲，能不能被浏览器直接打开取决于服务器 MIME；Word 只有一个自包含的 `.docx`，适合拿去 Word/WPS 继续编辑，但依赖内核自带的 pandoc、每次全量上传、页面上没有大纲与主题。FTP / SFTP / 本地目录都能配任一格式照常上传，只是 FTP 恒为单路串行、`LIST` 方言多，SFTP 仅支持密码认证。

| 项 | 说明 |
|---|---|
| 传输协议 | **WebDAV（默认，推荐）** / FTP / SFTP / 本地目录，四选一。四种协议各存一套地址、端口、用户名、密码、子目录，切换时互不覆盖；每次上传只使用当前选中的那一种 |
| 导出格式 | **HTML (SiYuan)**（默认，**推荐**）/ **Markdown** / **Word (.docx)**，三选一，与协议无关（换格式不换协议，换协议不换格式；四种协议都能配任一格式）。HTML (SiYuan) 传的是思源自己那一整套静态页面：`<文档名>/index.html` + `stage/`、`appearance/` 运行时 + 正文真正引用到的 `assets/`，离线打开、明暗主题、代码高亮、侧边大纲都在，还原度最高，代价是首次全量要把那套运行时带上（真实样本：一篇文档导出 549 个文件，其中 548 个是每篇都不变的运行时文件）。Markdown 传的是内核「导出 → Markdown」得到的那份正文（`<文档名>.md`，含前置元数据），加上同一内核导出目录里它真正引用到的 `assets/`：不带运行时、不注入侧边大纲，产物小一到两个数量级，适合喂给静态站点生成器或任何 Markdown 阅读器。Word 传的是内核「导出 → Word」的产物——思源自带的那套 pandoc 把正文排成**一个自包含的 `<文档名>.docx`**（图片在包里的 `word/media/`，实测与原图逐字节相同），远端目录因此只有两样东西：那个 `.docx` 和归属标记，没有 `assets/`、没有运行时；给 Word / WPS 继续编辑、或当附件发出去的是它。三处代价写在这里而不是藏在界面里：①内核的 Markdown 导出接口只吃文档 ID、不接受「含子文档」，所以选 Markdown 时那一档自动不生效，**历史记录里写的也是不含子文档**（不是「按你设的记」）；Word 与 HTML 相反，「含子文档」真生效（实测子文档被并进同一个 `word/document.xml`）。②Word 档要让内核把产物落在**工作区的绝对路径**下（`<工作区>/temp/export-docx/…`）：内核的 `savePath` 是逐字使用的，相对写法会按内核的工作目录解析、文件直接掉进思源的安装目录，所以内核没报告绝对工作区路径时插件当场失败并说明原因，绝不拿相对路径凑数。③三种格式落在同一个远端文档目录里，切格式后重新上传会把上一个入口文件当孤立文件清掉（`index.html` ↔ `<文档名>.md` ↔ `<文档名>.docx`），运行时也跟着一起摘。**没有 PDF 档，而且不是「还没来得及做」**：思源内核本身不产出 PDF——内核只有 `processPDF`（对已有 PDF 做加水印/书签/嵌入资产的 pdfcpu 后处理），真正的 PDF 字节来自桌面端编辑器窗口调用 Electron 主进程的 `printToPDF`，那条私有 IPC 要求一个可见的窗口，远程内核模式下直接被忽略。插件拿不到这条通道，也不假装能；要 PDF 请在思源里手动「导出 → PDF」，或把这一档的 `.docx` 用 Word 打开后另存为 PDF |
| 服务器地址 | WebDAV 填根 URL，如 `https://example.com/dav`；FTP/SFTP 填**主机地址**，如 `ftp.example.com` 或 `192.168.1.10`（IPv6 写成 `[::1]`，端口在右边的框里填），本地目录填绝对路径，如 `/var/www/html` 或 `D:\www\upload`。地址里的 `:2121` 写法**继续有效**，不必改动已配好的服务器。这一栏**边填边校验**：缺 scheme、串里混进空格会按当前协议给出正确示例并标红，而 `https://blog.example.com/dav`（思源挂在子路径反代后面，完全合法）**不标红**——这条正则的第一版连它自己的示例串都不通过，那是纯粹的误报；本地目录还额外拒绝含 `.` / `..` 的写法——这一条与上传时 `localBaseOf()` 用的是同一个规则（设置页此刻标红，好过让用户在删文件删到一半时才看到）；`localBaseOf()` 在此基础上还多拦一种：折叠后正好是整个磁盘根目录（设置页只看字面写法，看不出这种折叠）|
| 端口（FTP / SFTP） | 紧挨地址右侧的一栏：填服务器实际监听的端口，**留空＝用默认端口（FTP 21 / SFTP 22）**——框下灰字与 placeholder 都会把即将使用的端口说出来。优先级是**端口框 > 地址里的端口 > 默认端口**，两边各写一个且不一致时框赢、灰字当场标红并点名两个数字（一致时不提示）。WebDAV 与本地目录**没有这一栏**（整列隐藏）：WebDAV 的端口写在 URL 里，本地目录压根没有端口。端口跟协议绑定存在 profile 里，所以 FTP 可以待在 2121、SFTP 待在 2222，互不覆盖；它会一路带到访问地址（`ftp://host:2121/…`）、增量预检、SFTP 主机密钥指纹（`knownHosts["[::1]:2222"]`）与看板「查看上传路径」里那行地址——只有一处 `hostPortOf()` 在做决定 |
| 用户名 / 密码 | 对应协议的账号；SFTP 仅支持密码认证；本地目录留空 |
| 远端子目录 | 可选，如 `uploads`，所有文章放在这个目录下。**留空会亮出警告**：空前缀等于每篇文档的目录直接建在站点根上——跟站点自己的路径同名就会撞（比如一篇叫 assets 的文档），而且「删除远端文件」删的是根下面那一层；除非这个目录专门用来放上传产物，否则至少填一层子目录。不能含 `.` / `..` 段（会直接拒绝并说明原因，防止整树删除越界）；过长的中文标题会按 UTF-8 字节截到 120 字节以内并补 `-`，避免文件系统单段上限导致的 mkdir 失败 |
| 上传前清空远端旧目录 | 默认开。开启增量时不会整树删除（那会连运行时一起删、增量失去意义），只删本次目录内的孤立文件与改名残留目录；关掉＝**只追加、远端什么都不删**（一个会删文件的开关必须说清删什么、什么时候删） |
| 上传页面注入侧边大纲 | 默认开：大纲是在上传时就写进那份 HTML 里的，读者侧不需要再跑脚本、也不需要装浏览器扩展。注入的大纲可拖拽调宽度、可切靠左/靠右（默认靠左），长标题自动换行，目录按子树折叠展开（每条一个三角 + 标题栏折叠/全部展开，滚动定位会自动展开祖先）；正文在剩余空间居中、页面与大纲滚动条可见、把手让开滚动条；正文图片可点击放大（滚轮/按钮缩放、拖拽平移、Esc 关闭）；窄视口（≤760px）下大纲改成盖在正文上的抽屉、点按目标变大、灯箱认双指捏合/拖动/双击——同一份产物，不需要另出一版移动端页面；读者的停靠边与宽度记在浏览器 localStorage（手机上的抽屉开合不落盘） |
| 一键上传时包含子文档 | 默认开，决定右键那一个按钮是「单篇」还是「含子文档合并」 |
| 增量上传（跳过重复运行时） | 默认开，机制见「它解决什么问题」 |
| 单文件重试次数 | 1–6，默认 3；只重试瞬时故障（连接中断/超时/408/425/429/5xx，含 507/509），401/403/550 立刻失败不撞墙 |
| 并发上传数 | 0 = 按协议自动（WebDAV 6、SFTP/本地 4、FTP 1）；可手动 1–16，服务器弱或带宽小调低更快 |
| 单文件大小上限 (MB) | 默认 64，0 = 不限制；超限文件跳过并明确报错，避免整文件读进内存卡顿 |
| 自动改用服务器存得下的文件名 | 默认开（仅 WebDAV 链路生效）。附件/图片名里有 NTFS/IIS 存不下的字符（加号、冒号、问号、竖线、引号、尖括号、星号、反斜杠、结尾的点或空格，以及 `CON`/`NUL` 这类保留设备名）时，换成同形全角字符并同步改写页面里的引用；关掉后遇到这种名字会在写远端之前直接报错并列出问题文件。判定与映射规则见「服务器端注意」的 IIS 一条 |
| 输出调试日志 | 默认关。打开后在浏览器控制台输出每一次远端请求（一趟完整上传就是上千行），排查上传失败时用它。服务端回 4xx/5xx 的那几行**不受开关控制、始终记录**——思源的控制台是所有插件共用的，所以地址先去掉凭据再打印 |
| 已知主机密钥 (SFTP) | 显示已记录的指纹数量，「清除全部」用于换服务器/重装系统后重新接受指纹（TOFU 策略不会因为 README 说了却找不到入口而卡住） |

> **凭据存储说明（请知悉）**：服务器地址、用户名、密码以**明文**保存在插件配置里（思源工作空间 `data/storage/petal/siyuan-plugin-netglimmer-Upload/settings.json`，本机可读）。这是思源插件的通行做法——思源本身没有提供系统钥匙串级别的凭据存储接口，任何“加密”只要密钥还在本机，能读到你本机文件的程序同样能解密，所以这里不做假加密。实际风险与建议：①**不要**把整个工作空间目录（或 `data/storage/petal/` ）原样上传/同步到公开位置、网盘或聊天记录里；②把思源工作空间放在自己的账户目录下并开启磁盘加密（BitLocker/FileVault/LUKS）；③给上传用的服务器账号只授予目标子目录的写权限，不要用管理员账号；④换机器或分享配置时，手工把 `settings.json` 里的 `password` 字段删掉再分享；⑤设置页里每个文本框与数字框都向浏览器表了态（`name="netglimmer-upload-<键名>"` 加上明确的 `autocomplete`：密码框 `new-password`、用户名 `username`、服务器地址 `url`，其余一律 `off`），浏览器或密码管理器不会悄悄把一个存过的凭据填进这些格子里——被「好心」预填比留空更难查，因为连接报的错跟你实际输入的内容毫无关系。上传历史（`history.json`）不含密码，但会包含访问地址与文档名，同样按敏感处理。

每一档都对着手动导出的那一条内核接口，插件不额外加工：**HTML (SiYuan)** 走 `exportHTML`，参数与手动「导出 → HTML (SiYuan)」完全一致（是否添加标题等跟随思源「设置 → 导出」的全局配置），`index.html` 由内置的前端拼装代码逐字生成；**Markdown** 的正文就是 `exportMdContent` 的返回，一个字节不改；**Word (.docx)** 走 `exportDocx`，产物由内核自带的 pandoc 排好，插件传的是 `merge:` 跟随设置、「`removeAssets: true`」（图片已经嵌在包里，旁挂的那份 `assets/` 不要），然后原样上传内核落出来的那个 `.docx`。

填完地址和账号后可点「测试连接」：WebDAV 先 PROPFIND 探测可达性与认证再做写探针（MKCOL → PUT → DELETE）；FTP/SFTP 先登录，再自动做一次写探针（建目录 → 上传已知大小临时文件 → 核对尺寸 → 删除）。全部通过才建议保存。SFTP 首次连接会在提示中给出主机密钥指纹并记录（TOFU），之后指纹变化会拒绝连接，需在设置的「已知主机密钥 (SFTP)」一栏点「清除全部」后重连。

> FTP/SFTP 使用思源桌面端内置 Node 的直接 socket 连接，不经过内核转发代理，因此不必像 WebDAV 那样把整个文件读进内存再 base64 交给内核（体积约 1.33 倍）；代价是需要桌面端能直连服务器端口（公司代理/防火墙环境请先测试连接）。

## 使用

第一次配置时先读设置页**最上方**那条「★ 推荐组合：WebDAV + HTML (SiYuan)」：HTML (SiYuan) 是三档里唯一「一整页」的格式（明暗主题、代码高亮、侧边大纲、图片点击放大、双链与块嵌入都在），WebDAV 是普通 HTTP、也是端到端回归跑得最足的一条链路。没有特殊理由就照这一组配——要喂静态站点生成器或任何 Markdown 阅读器再换 Markdown，要交给别人在 Word/WPS 里继续编辑再换 Word。

文档树右键任意文档，只有 **Netglimmer 一键上传** 一个入口（编辑区标题图标菜单同名）。是否把子文档合并为一篇，由设置里的「一键上传时包含子文档」开关决定（默认开启），菜单上不按合并与否分条。文档上传过之后若又有编辑，该入口文案会变成 **「检测到改动，建议重新上传」**，直接点就是重传。右键点到的若是**文件夹**行，不会产生上传入口——只有文档才有。

不想翻菜单还有三个入口：**命令面板**里的「Netglimmer：上传当前文档 / 打开上传看板 / 重新上传全部有改动的文档」，以及**状态栏**上的「上传当前」「上传看板」。插件**默认不绑定任何快捷键**——快捷键的符号格式与用户既有绑定是否冲突，本机无从验证，抢走别人的键比少一个键更糟；请在 设置→快捷键 里自行搜索这三条命令绑定。找不到当前文档时只会提示，不会发出「猜出来的一篇」。

上传过程中右下角只有一个进度面板（阶段文字 + 按字节计算的进度条 + 当前文件名，刷新已节流不会刷屏），网络抖断会自动退避重试；面板上有一个 **「取消」**——取消是协作式的：**正在传的那一个文件会传完**再停（把在途请求掐断会在服务器上留下半截资产，下次增量按尺寸判断会把它当成好的）。取消之后的说法取决于取消落在哪儿：`index.html` 还没写出去 → 警告「远端此刻是不完整的」，记录写 `canceled/partial`，提示里给两条出路（重新上传补齐 / 删除远端文件清空该目录）；已经写完 → 普通提示「文件其实已全部传完，远端目录是完整的，只是没做完读回校验」。批量上传在篇与篇之间也能停，且**主动停下的不计入失败数**。成功后浮出**结果卡片**：上传路径单独一行、`user-select:all` 一点即全选，动作区**只有「上传看板」一个按钮**（不写剪贴板、不开新窗口——要这条路径的人自己全选、自己 Ctrl+C）。消息提示本身直接给出结论，形如：

`上传成功：file:///…/uploads/文章标题/index.html｜本次上传 1 个文件 / 20.9 KB，复用服务器上 548 个运行时文件，共 1 秒`

（FTP/SFTP 给出带端口的 `ftp://` / `sftp://` 远端路径。再次强调：这一行是**文件落在哪**，不是「打开就能看」的站点地址；能不能访问、用什么域名访问，取决于服务器有没有把这个目录当站点提供。）

**三种导出格式的产物形状**：HTML (SiYuan) 那一档，`<远端子目录>/<文档名>/` 下面是一整套静态页面，入口 `index.html`；Markdown 那一档是入口 `<文档名>.md` 加 `assets/`，`stage/`、`appearance/` 那几百个运行时文件根本不会被传出去；Word 那一档更少，目录里只有一个自包含的 `<文档名>.docx`（图片在包内）加一枚归属标记。结果卡片、看板「查看上传路径」展开的那一行、以及历史记录里的 `url`，写的都是**入口文件本身**（`…/<文档名>/index.html`、`…/<文档名>/<文档名>.md` 或 `…/<文档名>/<文档名>.docx`），不再是裸目录：一行目录路径既点不开，也说不清哪个文件是入口。Markdown 档正文里的链接写法由内核决定（只有空格转 `%20`，`:` `+` `#` `%` `(` `)` 原样留着），「自动改用服务器存得下的文件名」那档开关在这条链路上同样生效——远端把 `assets/a+b.png` 落成 `assets/a＋b.png` 时，正文里的 `](assets/a+b.png)` 会一起改写，空格那种写法（`](assets/a%20b.png)`）也认，两种输入形态都归到同一个安全名，否则读者点开的是断链。Word 档没有这条改写：图片在包里，服务器上不存在需要改名的资产文件，也就没有「链接与落地的文件对不上」这回事。

**文档树角标**：上传成功且内容一致的文档，标题后跟一个 🌐 角标；上传后正文又改过的，换成 ⬆ 警示色角标（鼠标悬浮有说明）。点击角标会带着 `noopener,noreferrer` 打开记录里那条远端地址（从思源里开出去的页面不许反手够到宿主窗口），而这枚角标一旦发现自己存着的地址与当前记录对不上就会被**重建**——重传到别的目录、或者改了文档名，都不许留下一枚点开「文件早就不在那儿」的旧地址；「能不能打开取决于服务器」，插件不承诺它是个站点（角标的 tooltip 把这句话写在上面）。

**上传看板**：插件设置面板「上传看板」页签，或状态栏「上传看板」打开。表格按时间倒序列出每条上传记录（时间、文档、协议、成功/失败、「本文」限定的文件数与字节数、远端路径、错误信息；同一文档同一协议只保留一条，重复上传仅刷新，文档名后面的 `×N` 是这篇上传过的次数），每列表头右缘都有一根可拖的把手，按住左右拖就能改这一列的宽度（双击把手只复位这一列，工具条「重置列宽」恢复全部七列），宽度记在浏览器 `localStorage` 里、下次打开还在；工具条右侧有提示文字，列宽也不会被拖到 0 或拖出上限。这组记下的宽度在**显示时**会被压进弹窗宽度：先让可伸缩的「详情」列让步，再按从宽到窄依次让步，任何一列都不低于它自己的下限——`localStorage` 里仍是你拖的那个值，窗口拉宽就恢复原样。这一「下限」**不是照着一种语言抄的常数**：时间 / 协议 / 结果 / 操作这四列内容不许折行，渲染时按当前界面上真排出来的格子量出它们要多宽，下限跟着抬——英文字典把徽标和按钮量宽了，列就一起变宽，而不是把字截掉。会折行的列（文档 / 详情 / 改动）不去撑宽，放不下就换行。同一套格子在真 Chromium 里量出来的下限是**中文 862px、英文 957px**（常数表 `DASH_COLS` 的 min 合计 829px，实测把「结果」与「操作」两列各抬起一档）；弹窗内容宽低于这个数时表格横向滚动是故意的（另一种做法就是再切掉一次「操作」列）。「详情」那一格前面钉着 **「本文」**：它是这篇文档自己的文件数与体积（正文 + 正文用到的资产），不含每次导出都顺带带去的 `stage/`、`appearance/` 运行时；表格上方那行摘要里的「实际传输 N 个文件 / 体积」才是这一次真正写进服务器的总量。两个口径本来就并存（第一次往某台服务器传一篇带图的长文，上方可能就是 571 个文件，格子里只有 2 个），不写出来读起来就像账算错了——所以限定词进文案，鼠标停在「详情」表头上还能看到这句说明；失败那一格的「详情」仍是错误原文，不带这两个字。表格上方有一行筛选：按文档名 / 路径 / 错误文本即时搜索（260ms 去抖），再按协议、结果、「只看有改动」缩小范围；点表头可以排序，排序方式记进 `localStorage`（那是习惯），筛选条件**故意不记**（那是一次性的意图）。工具条上还有两个批量按钮——**重新上传全部有改动**与**清理已删除文档的远端**——它们的作用范围就是**当前筛出来这一批**：先筛到某个笔记本再点，处理的就是那几篇；两者都只弹一次确认、串行执行、可以在篇与篇之间取消，并且把「失败」和「你主动停下的」分开计两个数。本地已删除、远端仍在的记录会被单独标出（注意：**进回收站的文档不会被认成已删除**——实测内核里回收站文档的 `blocks` 行仍然在，指纹查询回答“它还在”）。每行在「时间」列里有一个勾选框，工具条有**全选可删除项**与**删除所选 {n} 条**：勾哪几行就删哪几条记录（勾选集合会被当前筛选裁剪——把某行筛掉，它就不再是勾选状态，所以「删除所选」删不到你看不见的东西），单条、批量、筛选后单条、筛选后批量四种都做得到，不必再靠「清空记录」这一个出口。**远端还挂着文档的行勾不动**：勾选框禁用、光标 `not-allowed`、tooltip 指出出路是旁边那个「删除远端文件」。每行支持：

- **查看上传路径** —— 点一下在这条记录下面展开一整行路径原文（横跨全部七列、`user-select:all` 点一次即全选、长路径允许断行），按钮自己翻成「收起路径」，再点收回。不弹窗、不写剪贴板、不动远端，纯视图状态：看板一重绘（刷新、筛选、排序、重传完）展开就收回，因为路径不是需要长期盯着的东西。记录里没有路径信息时，那一行写「该记录没有远端路径信息」，不给你一行空白去猜。按钮 tooltip 直接就是路径本身，不点也看得清。
- **改动状态** —— 打开看板时自动批量比对源文档当前指纹与上传时指纹，标记「未改动 / 有改动 / 未知」，无需逐行点；
- **详情那一格** —— 悬浮说明写清三件事：本文自有文件数与体积、复用服务器上多少个、以及**有几个文件本次没能逐个确认**（服务器不答文件大小、或逐个确认达到上限时才出现）。第三个数字不只是浮出一句提示：它和这一次其它账目一起存进那条记录，所以九秒之后回到看板，账还在。
- **重新上传 / 重试失败项** —— 成功记录显示「重新上传」，失败记录显示「重试」，都会按该条记录当时使用的协议重传（而不是当前默认协议）；
- **试算** —— 只统计「会传哪些文件、共多少字节、能复用多少」，不建目录、不删除、不上传（远端零写入、不写历史记录），首次全量上传前用它确认体积最稳妥；
- **删除远端文件** —— 删除远端上这篇文档的上传目录，本地文档与历史记录保留，记录标为「已删除远端」、树角标同步消失。目录里有别人的归属标记时拒绝执行；记录里没有远端分段信息时只提示、不猜路径。
- **删除记录** —— 只把这一条**历史行**从清单里去掉：远端一个字节都不动，文档下次仍上传到同一个远端路径（归属标记还是它的）。按钮只出现在「远端不活着」的行上；判定用 `isLiveRec()`（`unpub` 一票否决，其余看 `pub`），`deleteHistoryRows()` 内部拿同一个谓词再判一遍，所以这道守卫不依赖界面有没有拦住。要真删服务器上的文件请走上面的「删除远端文件」，删记录不会删。

同一时间只跑一个上传任务：后点的会排队并提示「已排队」，上一个结束后自动开始，避免两个任务在远端互相删对方的文件。上传失败时如果远端目录已经建好或传了一部分，会额外提示「目录可能不完整」，并给出「先试算再重传」或「删除远端文件清空」两条明确出路。

看板保留最近 300 条记录，可一键清空。「清空记录」**依旧是无守卫的全清，但会把代价说出口**：如果里面还有远端仍挂着的文档，确认框会多一句「其中 {n} 条对应的文档远端还挂着……看板从此找不回它们」——清掉之后就再也找不到那批远端目录了。它仍然是一道无守卫的全清，因为这个按钮的意思就是全清；要精确删几行请用上面的勾选框 + 「删除所选」。

## 服务器端注意

- **IIS**：启用 WebDAV 发布功能后，注意 `web.config` 里 `webDAV` 的 `fileExtensions` 不能拦截 `.html/.css/.js/图片` 后缀；默认请求筛选会拒绝 `PUT` 中带点的某些扩展名，需逐项放行。另注意两件事：①**NTFS 决定了哪些名字根本存不下来**——路径段里不能有加号、冒号、问号、竖线、引号、尖括号、星号、反斜杠，不能以点或空格结尾，也不能是 `CON`/`NUL`/`COM1` 这类保留设备名（思源在 Windows 上导出时把附件原名一起带出来，所以这类名字会一路撞到 IIS；插件默认把它们换成同形全角字符并改写页面引用）。②**服务端自己有请求体上限**——IIS 的 `maxAllowedContentLength` 默认 28,969,706 字节（约 28.6 MB），`uploadReadAheadSize` 默认 64 KB（开 WebDAV 通常要调到几十 MB），超过就被拒；在真实 IIS 上实测 PUT 边界：20 / 27 / 28 MB 均 201，29 MB 与 30 MB 均返回 **413**。插件侧的「单文件上限」（默认 64 MB）管不到服务端这一层，所以一个 30 MB 的附件会一路撞到 413 才失败——报错会点名是哪个文件、多大，并提示调大服务端限制。另外 IIS 的 MIME 映射只影响**读取**（GET 服务），不影响 PUT：实测 `.mjs`/`.bcmap`/`.tmp`/`.py`/`.bat`/`.apk`/`.dat` 能存进去（201）但访问时返回 404，若上传的内容里引用了这类后缀，需在 IIS 里补 MIME 类型。③**Markdown 档的 `.md` 就在这条规则上**：真实 IIS 实测同一份 `.md` 能 PUT 进去（201）、PROPFIND 列得出、`getcontentlength` 与本地字节数一致，但 HTTP GET 回 **404**——文件在服务器上，是静态模块不给服务；要在浏览器里直接读到它，得给 IIS 补 `.md` 的 MIME 映射（`text/markdown` 或 `text/plain`）。Word 档的 `.docx` 不在这条规则上：同一台 IIS 实测 PUT 201、GET **200**，返回类型 `application/vnd.openxmlformats-officedocument.wordprocessingml.document`、字节数与本地一致——Office 后缀本来就在 IIS 的默认 MIME 表里，浏览器收到的是「下载 / 交给 Word 打开」，不是一张网页（本机 nginx 那台同样 200）。nginx 那台（本机 1.26.3，单独用 PUT/GET 探过，插件链路本身是在 IIS 上端到端测的）没有这条规则：GET 一个 `.md` 回 `200 application/octet-stream`，能下载，但浏览器不会当网页渲染。名字里带空格的那类安全名同样能服务：实测 `GET …/assets/safe%20name%EF%BC%8Bplus.png` 在这台 IIS 上 200 且字节一致（这条链接的编码必须原样发出，再套一层 encode 会变成 `%2520` 而 404）。
- **Nginx**：`dav_ext_module` 开启 `dav_methods PUT DELETE MKCOL;`，并加 `create_resources put;`（或依赖插件的 MKCOL）；`dav_access` 设置文件权限 `0644/0755` 以便 nginx 可读。另有三件事需要注意，都是本机 nginx 1.26.3（`dav` + `dav_ext`）上实测出来的，不是照着 IIS 推断：①**`client_max_body_size` 出厂只有 1 MB**，而每篇导出页面的运行时自带 `appearance/fonts/Noto-COLRv1-2.051/Noto-COLRv1.woff2`（1.9 MB）——出厂配置的服务器会在 WebDAV 看到请求之前就回一个光秃秃的 413（测试机上同一篇文档在默认配置下失败、改成 `client_max_body_size 60m;` 后上传成功）。附件通常比这更大，请按最大预期文件设置；插件侧的「单文件上限」抬不高服务端这一层。②**对集合的 `MKCOL` / `DELETE` 必须带尾斜杠**——不带时 nginx 回 409 且什么都不建 / 什么都不删（`DELETE` 那一条是回归脚本自己在删前缀时撞出来的：子项都清光了，前缀目录仍回 409；IIS 两种写法都收），插件已统一补齐。③**nginx 不会隐式创建多级目录**：想让服务器代劳就配 `create_full_put_path on;`，否则插件逐层自建，而 `PROPFIND Depth:0` 复核后仍然 409 的那种会被报成「父目录缺失」。两家都拒绝 `Depth: infinity` 的递归 PROPFIND（403），所以增量预检始终按 `Depth: 1` 一层层走。
- WebDAV 目录必须同时是网站静态资源目录（或反代映射），上传即可访问，无需重启任何服务。
- **FTP / SFTP**：插件把文件写到登录用户可写的路径（FTP 为登录后的当前目录，SFTP 为用户主目录）；若网站静态目录不在该路径下，请把远端子目录设为软链/挂载点可达的位置，或在服务器端把站点根指向该目录。SFTP 需服务器启用 `sftp` 子系统（OpenSSH 默认启用 `internal-sftp` 即可）。
- **FTP 中文文件名自动适配**：插件会探测服务器能力（FEAT/OPTS）。服务器声明 UTF8 时按 UTF-8 传路径；不支持 UTF8 的服务器（常见于中文版 Windows 上的 FileZilla Server / 老 IIS，按系统 ANSI 代码页 GBK 解释字节）会自动改用 GBK 编码路径，使磁盘上落成真中文名、浏览器可用正常 URL 访问（这条链路在本机是被证过的：一台拒绝 `OPTS UTF8` 的进程内 FTP 服务器上，路径确实按 GBK 码表发出、GBK 里没有的字符在动手之前就报错并点名，码表内的中文照常上传；中文版 Windows 真机（FileZilla Server / 老 IIS）本机没有，不写「已实测」）。
- **FTP 删除权限**：「上传前清空远端旧目录」与服务器的写探针清理需要 FTP 账号有删除权限。若服务器拒绝删除（如 FileZilla Server 未勾选 Delete），插件会自动改用固定名覆盖式探针并继续正常工作，但改名/删除旧文档留下的文件需要在服务器端手动清理——建议给 FTP 账号开启删除权限。
- **上传目录里的簿记文件**：每个上传目录会有一个小文件 `netglimmer-owner-<文档ID尾段>.json`（内容只有本文档 ID 与协议），插件用它判断「这个目录是谁的」，从而避免两篇同名文档互相删对方的内容。它会在静态目录列表里可见；如服务器端规则屏蔽 `netglimmer-owner-*`，页面访问不受影响，但同名冲突检测会失效（列不到标记＝当作没有主人）。

## 源码结构与打包（改代码的人看）

思源插件的运行时约定是「前端一次性执行 `index.js`」，没有 import 机制，所以**发布产物必须是单个 `index.js`**。本仓库在这个约束下做了最小程度的拆分：日常要改的逻辑都在主文件里，逐字移植/固定数据单独放，打包时用一个零依赖脚本拼回去。

```
siyuan-plugin-netglimmer-Upload/
├── src/
│   ├── core.js                  ← 日常在这里改：i18n 字典、helpers、FTP/SSH 客户端、
│   │                              上传器、容错（重试/并发池）、设置面板、看板、publish 主流程
```

日常流程：

```bash
node build.js          # 改完 src/ 之后生成 index.js
node build.js --verify # 只校验：磁盘上的 index.js 是否与 src/ 拼装结果逐字节一致（不写文件）
node build.js --check  # 只校验 src/ 内部一致性：标记与文件是否一一对应、有无孤立段
```

规则与坑：

- **不要直接编辑 `index.js`**——它是产物，下一次 `node build.js` 会被覆盖。改动一律进 `src/core.js`（或对应的 vendored 文件），再 build。
- `src/core.js` 里的 `/* @@VENDOR:名字@@ … */` 是拼装标记（注释形式，运行时是空语句）；`src/vendored/*.js` 里 `/* @@SEGMENT-BEGIN@@ */` 之后的内容会被原样拼回，**首尾不要增删空行**，否则 `--verify` 会失败。
- 这三段为什么要单独成文件：`index-html.js` / `gbk-table.js` 里有多条上万字符级的超长行（GBK 表那一行 70267 字符），混在主文件里会把每次 grep、diff、代码审阅都污染。分开之后 `src/core.js` 的 7558 行里最长行只有 371 字符，一条超过 500 字符的行都没有。
- 同步官方前端代码时（思源升级后 `buildIndexHtml` 相关实现可能变化）：先在思源里手动「导出 → HTML (SiYuan)」拿一份基准，再改 `src/vendored/index-html.js`，改完必须让上传产物的全量字节校验（`publish` 第 6.5 步，或本地 `run.js` / `run-multi.js` 回归）通过——这个插件的立身之本是「与手动导出逐字节一致」，不是「差不多就行」。
- 打包发布：`node build.js && node build.js --verify`，然后把 `index.js`、`plugin.json`、`icon.png`、`README.md`（英文，`readme.default` 指向它，缺了会在插件详情里显示为空白）、`README_zh_CN.md`、`i18n/` 压成 zip（不要把 `src/`、`build.js` 放进插件包，思源用不到）。`plugin.json` 的 `backends` 必须为空（本插件没有内核侧代码）、`frontends` 只能用思源真实存在的取值（`desktop` / `desktop-window` / `browser-desktop` / `browser-mobile` / `mobile` / `all`），`desktop-store`、`desktop-linux` 这类是无效值。
- 集市卡片图标：思源 3.8.6 只看**插件根目录下的 `icon.png`**——内核 `getInstalledPlugin` 在文件存在时才把 `iconURL` 填成 `/plugins/<插件目录名>/icon.png?v=<时间戳>`，前端拿它当 `<img src>`；文件不存在或加载失败，卡片就退回紫色商店占位图（实测：往目录里丢一个 `icon.png`，接口立刻开始返回该地址，`cmp` 校验返回字节与本地文件一致）。`plugin.json` 里**没有**图标字段，写 `icon` 也不会被读。图标由 `python3 tools/make-icon.py` 生成（512×512 RGBA，约 12 KB；脚本零依赖，自带浅/深色与 64px 缩略预览，用于确认小尺寸下仍读得出「文档 + 上传」）；打包脚本会校验它是正方形、带透明通道、边长在 256–1024、且不超过 60 KB。
- i18n 两份 JSON 是从 `src/core.js` 内嵌字典生成的，手改其中一份会在下次生成时被覆盖；新增文案请同时补 `zh_CN` 与 `en_US` 两处，并保证键集一致（回归脚本会断言）。

回归入口（`/root/harness/`，需要本地起着思源内核 16806 与 vsftpd 2121 / sftp 2222；vsftpd 的 `secure_chroot_dir` 指向 `/var/lib/vsftpd/chroot-empty`——那个空目录是 FTP 登录的前提，写在 `/var/lib` 而不是 `/tmp`，免得清理临时文件时把它端掉、让整套回归莫名其妙红在 FTP 那几步。那台 2222 的 sshd 同一个道理：配置文件是 `/root/harness/sshd2222.conf`，重启后用 `sshd -f /root/harness/sshd2222.conf` 就能把监听拉回来——放在 `/tmp` 里恰恰是清理扫描和重启最先带走的东西，而 SFTP 那几步红起来的樣子看着像插件的错）：

## 已知限制

- 导出格式三档：HTML (SiYuan)、Markdown、Word (.docx)（形状与代价见「配置」的「导出格式」一行）。reader 能不能在浏览器里直接打开，取决于服务器的 MIME 配置：`.md` 在这台 IIS 上默认回 404（nginx 回 200 但类型是 `application/octet-stream`），`.docx` 两家都回 200、浏览器行为是下载/交给 Word（见「服务器端注意」）。
- **PDF 不在支持范围内，原因是内核不给这条路**：思源内核的导出接口里没有 PDF，只有 `processPDF`——那是对**已有** PDF 做后处理的 pdfcpu 工具（加水印、加书签、把链接指向的资产嵌进去），它自己不排版，不传 PDF 进去就没有 PDF 出来。桌面端「导出 → PDF」的字节来自 Electron 主进程的 `printToPDF`：插件代码跑在渲染进程，要调它得走 `siyuan-get` / `siyuan-export-pdf` 这类私有 IPC，并且要求真的开出一个可见的编辑器窗口（远程内核模式下这条被直接忽略）。所以这一档不是「还没做」，而是插件这条路上没有可复用的 PDF 能力；替代路径写在设置项的说明里：思源里手动导出 PDF，或上传 Word 档那份 `.docx` 后用 Word 另存为 PDF。
- Word 档依赖思源自带的 pandoc（本机 3.8.6 随包带 3.10.1）。内核拒绝时插件把内核原文摊给你（`导出失败：` 后面那句就是内核给的原因，这个环境没有可用的 pandoc 是其中一种），不改用别的排版凑一个「看着像 Word」的文件——那种产物的字形、分页、目录都不会对得上，比失败更难排查。另外这一档要拿到内核报告的**绝对工作区路径**才能落临时文件：远程内核/路径缺失时当场失败并说明原因，不会退回相对路径（相对 `savePath` 按内核工作目录解析，实测会把产物写进思源的安装目录）。
- Markdown 档没有「含子文档」这一档：内核的 `exportMdContent` 只接受单个文档 ID。选 Markdown 时设置里的「一键上传时包含子文档」自动不生效，历史记录也按不含子文档写。Word 与 HTML 两档的「含子文档」都是真生效（Word 实测把子文档并进同一个 `word/document.xml`）。
- Word 档的 `.docx` 每次上传都是**全量**：它只有一个文件、没有可复用的运行时，增量在这条路上无事可做（历史记录里 `reused` 恒为 0）。同一次运行内的重复上传仍会去重成一行，不会堆历史记录。产物字节不保证跨时间逐字稳定（pandoc 会把生成时间写进包内的属性文件，实测同一篇文档隔一秒再导出会差一个字节），所以插件的改动检测用的是文档内容指纹而不是产物的哈希——「重传一次字节变了」不代表内容变了。
- 加密笔记本不支持上传（内核会拒绝明文导出）。
- WebDAV 的**每一次**读写都走内核 `/api/network/forwardProxy`：浏览器发不出 `PROPFIND`/`MKCOL` 这类动词，也带不上跨域的 Basic Auth，所以没有「浏览器通道」可回退（读文件字节倒是有一条回退链：XHR 相对地址 → fetch 相对地址 → fetch 绝对地址 → forwardProxy，取第一个非空结果）。写路径的代价是每个文件都要整个读进内存并 base64（体积约 1.33 倍）；FTP/SFTP 为桌面端直连 socket，不过内核。
- SFTP 仅支持密码认证（不支持私钥/passphrase）；主机密钥为 TOFU 策略，服务器换密钥后需手动清空已记录指纹。算法集合是刻意收窄的，服务器必须落在里面才连得上：KEX 为 `curve25519-sha256`（含 `@libssh.org`）或 `ecdh-sha2-nistp256`；加密为 AES-128/192/256 的 **CTR**（不提供 CBC，也不提供 AEAD——`aes*-gcm@openssh.com`/`chacha20-poly1305` 没有提案）；MAC 为 `hmac-sha2-256`/`512`，**带或不带 `-etm@openssh.com` 都支持**，所以只有非 EtM MAC 的老服务器（OpenSSH < 7.4、不少 NAS 里自带的 sshd）也连得上；主机密钥 `ssh-ed25519` / `rsa-sha2-256/512` / `ssh-rsa` / `ecdsa-sha2-nistp256`。完全没有交集时报错会点名服务器给出了哪些算法，而不是闷掉。严格 KEX 的「NEWKEYS 后序号归零」只在服务器自己也带 `kex-strict-s-v00@openssh.com` 标记时才做——不带标记的服务器自己不会归零，单方面归零恰好会把这批老服务器挡在门外。主机密钥的签名算法必须与协商值一致，协商 `rsa-sha2-512` 却回一份 SHA-1/SHA-256 签名会被拒绝。**没实现的一件事：会话中途换密钥（re-key）**。服务器发来的 KEXINIT 不会被响应，它的下一颗报文因此过不了 MAC 校验，链路上报为「连接丢失」，重试层会在下一个文件前重连一次——所以把 `RekeyInterval` 设得很短的服务器多花一次重连，但不会传坏。
- FTP / SFTP 接受 IPv6 地址，但**FTP 的数据传输仍只支持 IPv4**：它走 `PASV`，回复里只有四个 IPv4 字节（`EPSV` 未实现），所以纯 IPv6 的 FTP 服务器登录能过、开数据连接时会失败。SFTP（IPv6 已真机端到端覆盖）不受此限制；IPv6 主机还需要设置能直达服务器的路由。
- 并发上传按协议取上限（WebDAV 6 / SFTP 4 / 本地 4）；FTP 恒为 1 路串行——单控制连接下多路 STOR 的应答会互相咬住，属于协议限制而非实现偷懒。可在设置里手动覆盖并发数。
- 单文件默认上限 64 MB（设置可调，0＝不限制）：超限文件跳过并报错，因为整文件要读进内存做字节校验。WebDAV 还把每个文件 base64 后交给内核转发，所以这道上限其实是「内存 + 内核通道」的合计成本，而不是某个服务器的规矩。
- 同名文档的归属判定依赖上传目录里那个 `netglimmer-owner-*.json` 标记文件：服务器上手动删掉它、或用规则屏蔽该文件名时，两篇同名文档会被当成「目录没有主人」而各写各的（此时后上传的那篇会覆盖前者）。
- 「删除远端文件」只删该条记录里存的远端分段；记录里没有这个信息时插件不会靠猜路径去删（只提示手动处理）。要清掉那种目录，用同一协议重新上传一次（新记录会带上分段信息）或手动删除。
- 改动检测基于文档块索引（块数 + 最后更新时间），仅比较思源内源文档；上传后直接改远端文件不会被识别。
- 附件/图片名里有 NTFS 存不下的字符时（见「服务器端注意」的 IIS 一条），远端文件会被换成同形全角字符（`a+b.png` → `a＋b.png`），页面里的引用与 Markdown 正文里的链接同步改写；也就是说**服务器上的名字可能与思源里看到的不一样**（这是让整次上传成功的代价，本来就合法的名字不会被改）。另有两点是思源自身的限制：名字里带问号的文件根本不会被复制进导出目录（插件看不到它，也就无从改写，建议在思源里重命名）；把子树里两个附件改成同一个「安全名」时插件会自动补 `-2`/`-3` 后缀，但如果它们在服务器上原本就同名（例如只有大小写不同的两个名字，落在 NTFS 上就是同一个文件），仍需你在思源里改名。
- **没有任何一次网络等待是不封顶的**：每条路都有截止时间。一个永不返回的 `await` 是唯一一种「报错也报不出来」的失败——整次上传既不成功也不失败地悬在那里，用户只能重启思源。WebDAV 让内核的 `forwardProxy` 每个请求 90 秒后放弃（顺着代理读内核文件字节时给的是 60 秒，四步回退链里 XHR / fetch 那几步也按 60 秒截断）；FTP 控制连接空闲 30 秒超时，数据连接给 `STOR` 落盘 120 秒、给 `LIST`/`MLSD` 收完载荷 60 秒；SFTP 分段各给各的时限——banner 30 秒、`SERVICE_ACCEPT` 与 `INIT` 各 15 秒、认证 20 秒、单个 SFTP 请求 120 秒、默认每个等待应答 20 秒（banner 之后就把 socket 的空闲计时器摘掉，真正守着这条会话的是那些按请求计的时限）。超时一律按瞬时故障上报，所以重试层会重连而不是直接放弃。
- 「取消」是协作式的：**正在上传的那一个文件会传完**才停，所以取消一次只有一个超大文件的上传时要等那一次传输。中途掐断在途请求会在服务器上留下半截资产，而下一次增量上传按尺寸判断会把它当成好的——宁可慢一点，也不留说不清状态的文件。
- 「本地已删除、远端仍在」的判定来自文档块索引：**进回收站的文档不会被认成已删除**（本机内核实测：回收站里的文档 `blocks` 行仍然保留，指纹查询回答“它还在”）；它和改动检测吃同一条索引延迟，刚编辑几秒内的文档可能仍显示「无改动」。
- 命令面板与状态栏入口在有 `addCommand` 的宿主上走 `addCommand`、没有时回落到自己维护 `this.commands`，两条路径都在回归里对着「假宿主」跑过；但回归里没有真实的思源前端，**这三条命令在真面板里长什么样、点得到点不到属于结构推论**，请在思源里看一眼。
- 本地目录上传会拒绝含 `.` / `..` 段的配置路径，也拒绝折叠后正好是文件系统根目录的路径——因为重传与删除远端文件要在那个目录里**递归删除**，而 `path.resolve` 会把这类写法折叠到更短的根——`/` 也算一个。这么写的配置在读取时就被拒绝，设置栏同样会立刻标红，好过删文件删到一半才发现；要改请填一个普通绝对路径。
- 设置弹窗的排版与看板的几何都是**真量过的**：headless Chromium + 思源真实 CSS + saplay 行为移植。但它量的仍是那份**移植**的宿主，不是思源本身——换一个主题、或宿主改了 `Setting` 的实现都可能不一样；而且套件里只有 `run-layout.js` 用浏览器，大纲与灯箱那两组（`run-toc.js`）依旧是 DOM 桩——它们的观感结论属于结构推论，不是渲染实测。
- 看板的测量覆盖的是**设置弹窗里的「上传看板」页签**——状态栏与命令面板走的都是这个入口；独立的 `openDashboard()` 弹窗/页签仍旧只有结构性验证。像素同样来自 daylight 主题 + 默认字号：换主题、换字体或开缩放会得到另一组数，所以几何断言写成不变式（按钮 `clip === 0`、右边缘落在网格内、每列不低于**实测**下限）而不是写死像素——但 `run-dashview.js` 里的 `NEED_ZH` / `NEED_EN` 两张表**就是**本机像素数，字体明显更宽的环境可能凭空红几项，界面其实没坏。这里有一条更值钱的规则：**只量一遍等于只验了一种语言**——列宽的下限是内容宽，内容宽跟着字典走：同一张表在英文字典下徽标和按钮更宽（结果列要 142px、操作列要 266px），照中文配平的宽度就会截字、折行。所以看板是**两种字典各量一遍**，列下限在渲染时按当前界面重测；出现更长的语言时由测量兜住，不需要再手工配平一轮。至于「跨七列的淡底文字行到底像不像独立一行」——几何之外的那半仍然属于观感判断，`LAYOUT_SHOTS=1` 存下的 `browser/shot-dash-1600.png` / `shot-dash-1000.png` 就是给肉眼复核用的。
- FTP 目录列表的判定是对着**十种复现出来的服务器形态**做的（`run-ftpverify.js`：六种 `LIST` 写法、三种 `MLSD` 自引用条目、外加一台在某个子目录上列失败的），不是对着某一台真实的机器——连不上的服务器没法测，所以总可能有一种方言没被覆盖到。如果上传结束时仍有文件「未能逐个校验」，提示语会带上服务器原始 `LIST`/`MLSD` 回复的 120 字符样本：它该被读成「插件读不懂你的目录列表」，不是「你的文件丢了」，而那个样本正是把问题说清楚所需要的那句话。
- 看板删除记录删的**只是历史行**——远端一个字节都不动，记录被删掉的文档下次仍上传到同一个远端路径（归属标记还是它的）。远端还挂着文档的行勾不动、也没有「删除记录」按钮；要真删文件请先用「删除远端文件」。「清空记录」仍然**没有守卫**，会把包括远端活着的那些行一起清掉——所以它的确认框会报出这个数量：清完之后，看板就不是回到那批远端目录的路径了。
