# Netglimmer Upload (`siyuan-plugin-netglimmer-Upload`)

One click **uploads** a document to a WebDAV / FTP / SFTP server or a local folder, in one of three export formats: a byte-identical "HTML (SiYuan)" page, plain Markdown plus the assets it references, or a single self-contained Word (.docx). With "HTML (SiYuan)" selected, backlinks, block references, block embeds and image assets all survive — the uploaded page renders exactly like the official "share document" output.

> **This plugin does exactly one thing: it puts files on a server.** It does not deploy a site, does not manage ports, does not issue certificates. Whether that folder can be opened in a browser, and under which domain, is decided by the server (IIS / nginx / an alias mapping / a mount point) — the plugin neither knows nor can guess. So the UI says "upload", not "publish", and the row offers **Show path** instead of an Open / Copy pair: it spreads open the directory the files actually landed in, and leaves the rest of the road to you.

Chinese documentation: [`README_zh_CN.md`](README_zh_CN.md) (more detailed).

## What it automates

The manual loop "export HTML → copy into the web root" has two problems: you redo it after every edit, and the target folder accumulates stale files. This plugin does the whole chain for you:

right-click → export in the format currently selected in settings (HTML (SiYuan) / Markdown / Word) to SiYuan's temp folder → concurrent PUT upload → read-back byte verification of every file → temp cleanup.

Re-uploading the same document is incremental by default: the SiYuan *runtime* (the 548 byte-identical `stage/` + `appearance/` files that every HTML export carries along) is skipped when the server already has it, so a second upload of the same document pushes ~20 KB instead of 34 MB. Markdown and Word have no runtime to reuse — what goes up is the body and the handful of files it references. A stale directory left behind by a document rename or move is cleaned up automatically, and two documents with the same title never overwrite each other — each folder carries an ownership marker.

> SiYuan 3.8.6: the kernel's HTML export API does not write `index.html` at all (the front end assembles it and saves it through a separate API). The plugin ships a verbatim port of that assembly code, so the uploaded `index.html` is byte-for-byte identical to a manual "HTML (SiYuan)" export. Markdown and Word need none of that: the kernel hands back the finished product — a `.md` body in one case, a pandoc-laid `.docx` in the other — and the plugin uploads those bytes untouched.

## Protocols

| Protocol | Transport | Notes |
|---|---|---|
| WebDAV — **the recommended transport** | kernel `/api/network/forwardProxy`, always (there is no browser leg to fall back to) | A browser cannot send `PROPFIND`/`MKCOL` cross-origin and cannot attach Basic Auth to them, so every verb — including `PUT` — goes through the kernel; each file is read into memory and base64-encoded on the way (≈1.33× the body). Pairs with the default HTML (SiYuan) format (see the settings note above) |
| FTP | built-in pure-JS client over the desktop Node `net` socket | PASV; auto-detects UTF8 support and falls back to GBK paths on Chinese Windows servers that do not declare UTF8 |
| SFTP | built-in pure-JS SSH-2 / SFTP v3 client (password auth) | TOFU host key pinning; no external binaries required |
| Local folder | desktop Node `fs` | Any absolute path, e.g. `/var/www/html` or `D:\www\upload` |

Each protocol keeps **its own** server / port / username / password / sub-directory profile; switching protocols swaps the whole profile, so a WebDAV setup never leaks into the FTP form. Uploading always uses the currently selected protocol only.

FTP and SFTP have a **port box** next to the address (empty = 21 / 22). The spelling `192.168.1.10:2121` inside the address also keeps working — if both are filled, the box wins and the field turns red while they disagree. WebDAV keeps carrying its port inside the URL, and a local folder has no port at all, so the box is hidden for both.

## Install

Unzip into `{workspace}/data/plugins/siyuan-plugin-netglimmer-Upload/` and restart SiYuan. Desktop only.

> Settings and upload history are read from, and written to, **only this plugin's own id** (`siyuan-plugin-netglimmer-Upload`). Nothing is read from another plugin's storage and no other configuration shape is ever converted: a workspace that has no data under this id starts with empty settings and an empty history, and the first upload asks for the server credentials.

## Settings

Open SiYuan "Settings → Plugin market / Loaded plugins → Netglimmer Upload". Triggering an upload without a saved configuration opens the panel for you.

> **Recommended combination: WebDAV + HTML (SiYuan).** The plugin pins this at the **very top** of its settings view, before the first setting row, for the reasons the table below spells out: HTML (SiYuan) is the only one of the three formats that is a whole page — light/dark themes, code highlighting, the side outline, click-to-zoom images and block references/embeds all survive, and it opens offline as that same complete page, so it is the most faithful to SiYuan's own styling. WebDAV is plain HTTP (`PUT`/`DELETE`/`MKCOL`/`PROPFIND`), which no browser, proxy or firewall picks apart, and it is the path this suite's end-to-end regression runs hardest (a real IIS server and nginx each get a full pass with byte-for-byte read-back). The other two formats each trade something away: Markdown is the body plus the images it actually references — no runtime, no injected outline, and whether a browser opens it inline depends on the server's MIME map. Word is one self-contained `.docx`, the right thing to hand someone who will keep editing in Word or WPS, but it depends on the pandoc bundled with the kernel, uploads in full every time, and puts no outline or theme on the page. FTP / SFTP / the local folder carry any of the three formats normally; their caveats are that FTP is always single-connection with several `LIST` dialects and SFTP supports password authentication only.

**Credential storage (please read):** server, username and password are stored in **plaintext** in `data/storage/petal/siyuan-plugin-netglimmer-Upload/settings.json` inside your workspace. That is standard for SiYuan plugins: SiYuan offers no keychain-grade storage API, and any "encryption" whose key also lives on the same machine only deceives the reader, not an attacker — so we do not ship fake encryption. Mitigations: ① never sync or share the workspace (or `data/storage/petal/`) as-is; ② keep the workspace on a disk-encrypted volume (BitLocker / FileVault / LUKS); ③ give the upload account write access to the target sub-directory only; ④ delete the `password` field before sharing a config; ⑤ the settings fields themselves declare `name="netglimmer-upload-<key>"` plus an explicit `autocomplete` (`new-password` for the password, `username` and `url` where they apply, `off` everywhere else), so the browser or a password manager does not quietly drop a stored credential into the box — a prefilled value is worse than an empty one, because the connection then fails for a reason that has nothing to do with what you typed. `history.json` holds no passwords but does contain remote paths and document names — treat it as sensitive too.

Test the connection before saving: WebDAV runs a PROPFIND reachability/auth probe then a write probe (MKCOL → PUT → GET read-back → DELETE); FTP/SFTP log in and then create a folder, upload a file of known size, verify its size and delete it. SFTP reports and records the host key fingerprint on first contact (TOFU) and refuses to connect if it changes later — clear it under "Known host keys (SFTP)".

## Usage

Before the first upload, read the **"★ Recommended: WebDAV + HTML (SiYuan)"** block pinned at the **top** of the settings view: HTML (SiYuan) is the only format that stays a whole page (light/dark theme, code highlighting, side outline, click-to-zoom images, block references and embeds), and WebDAV is plain HTTP — the transport the end-to-end regression exercises hardest. Absent a specific reason, configure that pair; switch to Markdown to feed a static-site generator or a Markdown reader, and to Word to hand the file to someone who will keep editing it.

Right-click any document in the file tree (or the title icon in the editor): the **first row is always "Netglimmer One-Click Upload"**, and it uploads with the **current settings**. Whether sub-documents get merged into one page is a setting (`Include sub-documents`, on by default), not a second menu row. If the document was edited after its last upload, a **second row appears — "Changes detected — re-upload"** — and that one re-uploads with the protocol and merge mode **of that record**, not as a fresh upload under today's settings (you right-clicked the document, not the upload parameters). Anything that cannot be decided is not offered: no *live* successful record (the newest one may have had its remote deleted), no stored fingerprint, or a failed fingerprint query leaves exactly the one row, because a second button that would only re-write the same remote files is worse than no button at all. When the newest record's remote was deleted but an older record is still live, the second row follows the **live** record's protocol and merge mode. (Right-clicking a *folder* row contributes no upload entry — only documents get one.)

Three more entry points exist for the same actions, so you never have to find the right row: **"Netglimmer: Upload the current document"**, **"Netglimmer: Open the upload dashboard"** and **"Netglimmer: Re-upload every changed document"** are in SiYuan's command palette (bindable to a hotkey by you — the plugin deliberately ships none), and the first two also sit in the status bar.

While uploading you get a single progress panel in the bottom-right (phase text, byte-based progress bar, current file name, throttled) with a **Cancel** button. Cancelling is cooperative: the file being uploaded finishes first, then the upload stops and tells you what state the remote is in — before `index.html` was written the folder is incomplete (warning, and the record keeps a re-upload entry), after it the remote is already a complete page (informational). Transient network faults retry automatically. A successful upload ends with a result card whose **path line is click-to-select**, and whose action area holds exactly **one button: "Upload Dashboard"** — there is no Open button, no Copy button and no automatic clipboard write; if you want the path, select it and copy it yourself. The final message states the outcome, e.g.:

`Uploaded: file:///…/uploads/article-title/index.html | this run uploaded 1 file / 20.9 KB, reused 548 runtime files already on the server, 1 s`

(FTP/SFTP report an `ftp://` / `sftp://` remote path, with the port when one is set. To repeat the point: that line says **where the files landed**, not "a URL that opens" — whether anything serves that folder, and under which hostname, is the server's business.)

What each export format leaves on the server: HTML (SiYuan) fills `<remote sub-directory>/<doc-name>/` with a whole static page bundle whose entry is `index.html`; Markdown leaves the entry `<doc-name>.md` plus `assets/` there — the several hundred runtime files under `stage/` and `appearance/` are never uploaded; Word leaves even less, one self-contained `<doc-name>.docx` (images inside the package) plus the ownership marker. The result card, the "Show path" row in the dashboard and the `url` stored in history all point at **the entry file itself** (`…/<doc-name>/index.html`, `…/<doc-name>/<doc-name>.md` or `…/<doc-name>/<doc-name>.docx`) rather than the bare directory: a directory path opens nothing and does not say which file is the entry. In Markdown mode the kernel writes the links (only a space becomes `%20`; `:` `+` `#` `%` `(` `)` stay literal), and the server-safe-names switch works on that path too — when the remote stores `assets/a+b.png` as `assets/a＋b.png`, the body's `](assets/a+b.png)` is rewritten with it, and the percent-encoded spelling `](assets/a%20b.png)` is recognized as well, both folding onto the same safe name; otherwise the reader clicks a broken link. Word mode has no such rewriting to get wrong: nothing is stored beside the file, so there is no link that could point at a missing asset.

**File-tree badge**: a 🌐 globe sits right after the title of any uploaded document; after you edit it, the badge becomes an amber ⬆. Clicking either opens the remote path recorded for it with `noopener,noreferrer` (a page opened from inside SiYuan must not be able to reach back into the host window), and the badge is **rebuilt** as soon as the address stored for that document stops matching what it was drawn with — re-uploading into another folder, or renaming the document, must not leave a badge that opens a path the files no longer live at. The badge's tooltip says so honestly ("whether that works depends on the server actually serving the folder as a site"). It is the one "Open" left in the plugin, because it lives on the badge rather than in the dashboard or the card, and cutting it would take a handle people actually use away.

**Upload dashboard**: the "Upload Dashboard" tab in the settings dialog, or the status-bar entry. Records are newest first (time, document, protocol, result, **this document's own** file/byte counts, remote path, error; one row per document + protocol + include-sub-documents setting, re-uploading just refreshes it, and a `×N` badge on the document shows how often that document has been uploaded). Above the table a filter row searches document name / path / error text and narrows by protocol, result or changed-only; clicking a header sorts (that preference is remembered, the filter is deliberately not — it is a passing intent). **Bottom-right of the table is the pager**: "Items {a}–{b} of {N}", Previous / "Page {p} / {n}" / Next, and a **per-page** dropdown (10 / 20 / 50 / 100 / All, default 20). Page size is a habit, so it is remembered in `localStorage` — same treatment as the column widths and the sort, and it does not sync with the note; **the page number is a passing intent and is not remembered**, and any of these puts you back on page 1: leaving the tab, typing in the search box, changing protocol or result, ticking changed-only. A page number that stops existing (a filter shortened the list, a bigger page size left less work to do) is clamped to the last real page rather than showing an empty screen. With one page, Previous and Next both stay in place **greyed out** — buttons that vanish with the row count make the toolbar jump. The one scope to keep straight: **paging only decides how many rows this screen draws** — filtering, sorting, the ticks and the three bulk actions always apply to **the whole filtered result**, so page 3 does not forget the ticks from pages 1–2, and the N in "Delete {n} selected" counts them. Each header cell carries a drag handle on its right edge to resize that column (double-click the handle to reset just that one, or use **Reset column widths** in the toolbar); widths are remembered per browser. Those remembered widths are **fitted for display** when the dialog is too narrow to hold them all: the 详情 column gives way first, then the widest columns in turn, never below each column's own minimum — `localStorage` still holds what you dragged, so widening the dialog restores your real widths. That minimum is **not** a constant copied out of one language: for the four columns whose content must not wrap (时间 / 协议 / 结果 / 操作) it is **measured from the cells actually on screen** at render time, so an English pill or a row of English buttons widens the floor instead of being truncated — and the measurement includes each header's own label, because a header cell is the one thing on this grid that has no overflow handling: it cannot be ellipsised, so a column name that does not fit simply prints over its neighbour's name (a floor sized only by cell content would let `Protocol` land on top of `Result`); a column that is allowed to wrap lets its header wrap too. Measured in Chromium, those floors come to **862px** of Chinese content and **966px** of English content against a grid that is 1142px wide at a 1600px dialog — so below roughly 1000px of dialog content even the floors do not fit and the table scrolls sideways on purpose, which beats cutting the 操作 column off again. The 详情 cell is prefixed **「本文」** (`Doc only:` in English) and its header carries a tooltip, because two different totals live on this one table: the cell counts only the document's own files — its body plus the assets it references — while the line above the table says 实际传输 / "sent" N files, which is what really reached the server this run and still includes the `stage/` and `appearance/` runtime every export drags along (a first upload of a long illustrated note can read 571 files above and 「本文 2 文件」 in the cell). Two numbers that differ by that much, with nothing saying why, read as an accounting bug rather than as two bases — so the qualifier is in the copy, not only in a tooltip. A failed row's 详情 stays the error text and carries no prefix. The two toolbar buttons — **Re-upload all changed** and **Clean up deleted documents** — act on **the rows currently filtered**, one confirmation each, and can be stopped between documents. Rows whose document no longer exists locally are marked (note: a document sitting in SiYuan's trash is *not* detected as deleted). Every row has a checkbox in the Time column, and there are **two select-all handles** whose scopes are written on their own tooltips: **the master checkbox at the very front of the Time header covers the current page** (tri-state — checked only when the whole page is ticked, `indeterminate` when half of it is, entirely disabled when every row on that page is still live on the server), while **"Select all ({n} filtered)" in the toolbar covers the whole filtered result**, including the pages the pager cannot reach; the `{n}` in its label is exactly how many rows that click can tick, and it turns into "Clear selection" once they all are. **Rows whose files are still live on the server enter neither handle.** **"Delete {n} selected"** removes records from this local list only — it sends not one remote request, is grey while nothing is ticked, and reports the real N in its confirmation. **The tick set is pruned by the current filter**: filter a row away and it stops being ticked, so "Delete {n} selected" can never delete something outside the batch you are looking at — while keeping ticks across pages is precisely the point of "Select all ({n} filtered)", and the N counts them. Single, batch, filtered-single and filtered-batch all work; "Clear history" is not the only exit. Each row offers:

- **Show path** — one click expands the full path as its own text row underneath that record: it spans all seven columns (`grid-column:1/-1`), is `user-select:all` so a single click selects the whole string, and breaks long paths instead of forcing the table wider. The button turns into "Hide path"; clicking again collapses it. Its tooltip *is* the path, so you can read it without clicking. A record with no stored path expands to "This record has no remote path" rather than an empty line you have to interpret. The expanded state is deliberately **not** persisted: any re-render (refresh, filter, sort, a re-upload finishing) collapses it, because a state machine for one line is not worth it. It writes nothing, calls nothing remote, never opens a window and never touches the clipboard — `run-dashview.js` asserts exactly that. The expanded row carries its own padding, a faint tint and a bottom border, so the seven cells' `border-bottom` does not sit *above* the path and make the path read like the start of the next row.
- **Change status** — filled in automatically by one batch query when the dashboard opens: unchanged / changed / unknown.
- **The Details cell** (`Doc only: …`) — its tooltip carries three numbers: this document's own file count and size, how many files were reused on the server, and **how many files could not be confirmed one by one** this run (only when the server withholds sizes or the per-file check hit its cap). That last one is not just a nine-second toast: it is stored in the record alongside the rest of the accounting, so the numbers are still on the dashboard after the toast is gone.
- **Re-upload / Retry** — always uses the protocol that record was uploaded with, not the current default.
- **Dry run** — computes which files *would* be uploaded, their total size and how much could be reused, and writes nothing at all (no mkdir, no delete, no upload, no history row). The cheapest way to sanity-check a first full upload.
- **Delete remote** — deletes this document's remote folder; the local document and the history row stay (marked "Remote files deleted", tree badge disappears). Refused when the folder carries another document's ownership marker; a row with no stored remote path segments gets no delete button at all, because the plugin never guesses a path from the display URL.
- **Delete record** — drops **only the history row**: nothing on the server is touched, and the document keeps uploading to the same remote path (its ownership marker still says it is yours). The button appears on rows that are not live on the server; a row whose document is still there has a `disabled` checkbox and no delete button, and its tooltip points at "Delete remote" as the way out. `deleteHistoryRows()` re-checks the same predicate internally, so the guard does not depend on the UI.

Only one upload runs at a time; a second click is queued and starts automatically, so two tasks can never delete each other's files. If an upload fails after the remote folder was created or partially uploaded, the message says the folder may be incomplete and points at "dry run then re-upload" or "delete remote files to clear it".

## Server notes

- **IIS**: after enabling the WebDAV *publishing* feature (that is Microsoft's own name for it, not this plugin's vocabulary), `webDAV` → `fileExtensions` in `web.config` must not block `.html/.css/.js`/images, and request filtering needs the relevant extensions allowed for `PUT`. Two more things bite in practice: ① **NTFS decides which names cannot exist** — a path segment cannot contain `+ : ? | " < > *` or a backslash, cannot end in a dot or a space, and cannot be a reserved device name (`CON`/`NUL`/`COM1`); Windows SiYuan exports attachments under their original names, so such a name reaches IIS verbatim and would otherwise kill the whole upload at the last step with a bare 400/404 — by default the plugin rewrites it into a full-width look-alike and fixes the page references. ② **The server caps the request body itself** — IIS `maxAllowedContentLength` defaults to 28,969,706 bytes (~28.6 MB) and `uploadReadAheadSize` to 64 KB (WebDAV usually needs tens of MB); measured on real IIS: PUTs of 20/27/28 MB return 201, 29/30 MB return **413**. The plugin's per-file limit cannot raise this — a 30 MB attachment will therefore fail at the server side, and the error names the file, its size and this limit. Also note the MIME map restricts GET (serving), not PUT: `.mjs .bcmap .tmp .py .bat .apk .dat` store fine (201) but 404 when served — add the extensions to IIS if an uploaded page references them. ③ **Markdown mode's `.md` is exactly this case**: measured against real IIS, the same `.md` stores fine (PUT 201), shows up in PROPFIND with a `getcontentlength` matching the local byte count, and still returns **404** to a plain HTTP GET — the file is on the server, the static-file module just refuses to serve an extension that is not in the MIME map. Add `.md` (`text/markdown`, or `text/plain` to be read in the browser) if readers should open it. Word mode's `.docx` is not subject to that rule: on the same IIS, PUT returns 201 and GET returns **200** as `application/vnd.openxmlformats-officedocument.wordprocessingml.document` with a byte count matching the local file — Office extensions are already in IIS's default MIME map, so a reader gets "download / open in Word" rather than a web page (the local nginx box serves it 200 as well). The local nginx 1.26.3 box (probed with PUT/GET directly; the plugin path itself is covered end-to-end against IIS) has no such rule and answers `200 application/octet-stream`, which downloads rather than renders. Space-containing safe names do get served: `GET …/assets/safe%20name%EF%BC%8Bplus.png` returns 200 with matching bytes on that IIS — with the caveat that the escaping written in the document body must go out verbatim, since percent-encoding it a second time turns `%20` into `%2520` and 404s.
- **Nginx**: `dav_methods PUT DELETE MKCOL;` plus `create_resources put;`, and `dav_access` permissions of `0644/0755` so the worker can read what was written. Three more things matter, all measured against a local nginx 1.26.3 with `dav_ext` rather than assumed: ① **`client_max_body_size` defaults to 1 MB**, and the exported page's own runtime needs more than that — `appearance/fonts/Noto-COLRv1-2.051/Noto-COLRv1.woff2` is 1.9 MB, so a stock server fails the upload with a bare 413 before WebDAV ever sees the request (measured on the test box: the same upload fails at the nginx default and succeeds with `client_max_body_size 60m;`). Attachments are usually bigger still, so set it above your largest expected file — the plugin's own per-file limit cannot raise it. ② **`MKCOL` and `DELETE` on a collection only work with a trailing slash** — without one nginx answers 409 and creates nothing / deletes nothing (IIS takes both), which the plugin now normalizes. The `DELETE` half of that was discovered by the Word regression script itself: it had emptied every child of its prefix yet the prefix directory still answered 409, because nginx reads a slash-less name as a *file*. The retry-with-slash is now in the helper, and the "my prefix is gone" assertion runs after it. ③ **Nested directories are not created implicitly**: put `create_full_put_path on;` if you want the server to build missing ancestors, otherwise the plugin creates them level by level and a 409 that survives a `PROPFIND Depth:0` re-check is reported as "parent missing". `Depth: infinity` PROPFIND is refused by both nginx and IIS (403), so the recursive listing is always `Depth: 1` per level.
- Whether an uploaded folder is *reachable as a web page* is entirely the server's arrangement: the WebDAV directory has to be the site's static resource directory (or reverse-mapped to it) for a browser to show it. The plugin uploads and reports the path; it does not probe reachability, because the plugin makes no promise about a site address it cannot verify. No service restart is needed for the files themselves.
- **FTP / SFTP** write into the login user's writable path (FTP: current directory after login; SFTP: home). Point the remote sub-directory at a symlink/mount reachable from the web root, or aim the site at that folder.
- **Bookkeeping file in each uploaded folder**: `netglimmer-owner-<document-id-suffix>.json` (a few dozen bytes containing only the document id) tells the plugin who owns a folder, which is what stops two same-titled documents from wiping each other. The name deliberately has **no leading dot**: vsftpd defaults to `hide_dotfiles=yes` and such a file would never appear in an FTP LIST/MLSD, silently disabling collision detection. Blocking the name with a server rule leaves browsing intact but loses that protection.
- **FTP delete permission** is required by "clear remote folder first" and by probe cleanup. If the server refuses deletes, the plugin switches to a fixed-name overwrite probe and keeps working — but renamed/deleted leftovers then need manual cleanup, so granting delete is preferable.

## Source layout and build (for maintainers)

SiYuan front ends execute a single `index.js`, so the shipped artifact must be one file. The repository splits review-friendly code from fixed/vendored data and splices it back with a dependency-free script:

```
siyuan-plugin-netglimmer-Upload/          ← the plugin folder name (must match `plugin.json` → `name`; the name of your own checkout directory is irrelevant)
├── src/
│   ├── core.js                  ← everything you normally edit: i18n dicts, helpers, FTP/SSH
│   │                              clients, uploaders, resilience (retry/pool), settings UI,
│   │                              dashboard, publish() main flow (`publish` is only the internal
│   │                              function name; every user-facing string says upload)
│   └── vendored/
│       ├── index-html.js        ← verbatim port of SiYuan 3.8.6's index.html assembly
│       ├── toc.js               ← side-outline payload + injectToc
│       └── gbk-table.js         ← GBK/Unicode code page table (one ~67 KB base64 line)
├── build.js                     ← splicer (Node fs only, no npm deps)
├── index.js                     ← artifact: core.js + the three vendored segments
├── plugin.json
├── icon.png                     ← marketplace card icon (512×512 RGBA, made by tools/make-icon.py)
├── tools/make-icon.py           ← dependency-free icon renderer (pure Python, no PIL/cairosvg)
└── i18n/{zh_CN,en_US}.json      ← generated from the dict embedded in src/core.js
```

```bash
node build.js           # regenerate index.js after editing src/
node build.js --verify  # prove index.js on disk equals the splice, byte for byte (no writes)
node build.js --check   # only internal consistency: markers ↔ files, no orphan segments
```

Rules and traps:

- **Never edit `index.js`** — it is generated and will be overwritten.
- `/* @@VENDOR:name@@ … */` in `src/core.js` are splice markers (comments, no-ops at runtime); everything after `/* @@SEGMENT-BEGIN@@ */` in `src/vendored/*.js` is pasted verbatim, so do not add or remove blank lines at its edges or `--verify` fails.
- When porting new front-end code after a SiYuan upgrade, first export "HTML (SiYuan)" by hand as a baseline, then change `src/vendored/index-html.js`, and the full byte verification inside `publish()` (or the local regressions) must pass. This plugin's whole value proposition is "byte-identical to a manual export", not "close enough".
- The two i18n JSON files are generated from the dictionary embedded in `src/core.js`; add every new string to both locales (the regression asserts identical key sets).
- Packaging: `node build.js && node build.js --verify`, then zip `index.js`, `plugin.json`, `icon.png`, `README.md`, `README_zh_CN.md`, `LICENSE`, `NOTICE`, `i18n/`. Do not ship `src/` or `build.js` inside the plugin zip. `backends` must be empty (there is no kernel-side code) and `frontends` may only use values SiYuan actually has (`desktop`, `desktop-window`, `browser-desktop`, `browser-mobile`, `mobile`, `all`) — `desktop-store` / `desktop-linux` are invalid.
- Marketplace icon: SiYuan 3.8.6 only looks for **`icon.png` in the plugin's root folder**. `getInstalledPlugin` fills `iconURL` with `/plugins/<dir>/icon.png?v=<timestamp>` when that file exists, and the card uses it as `<img src>`; otherwise (or on load error) it falls back to the generic store placeholder. There is no icon field in `plugin.json`. Regenerate with `python3 tools/make-icon.py` (512×512 RGBA, ~12 KB, zero dependencies, and it also renders light/dark and 64 px previews so the document-plus-upload glyph stays legible at card size).

Each of those six cases also reads the two controls the grid gained: every header cell is measured for **its own label** — the overhang of the absolute `colGrip` is credited to the handle (`clip <= gripOver`) while text, sort arrow and the page's master checkbox must stay inside the cell's right padding (`textOver <= 0`), which is what caught `Protocol` printing over `Result` in the English dictionary — and the pager strip is read as one box (no horizontal overflow, its right edge inside `.b3-dialog__content`, every child unclipped, the size `<select>` holding exactly the plugin's own `DASH_PAGE_SIZES` and sitting on `DASH_PAGE_SIZE_DEFAULT`, both arrows present and both greyed when the seed fits on one page) plus the master checkbox in the 时间 header (a real `input[type=checkbox]` with a non-empty tooltip and a non-zero box).A second group clicks the first path button and asserts the band spans all seven columns from `left:0`, sits below its own row, computes `user-select: all`, does not overflow horizontally, and collapses on the second click. A third group **drags a real handle in Chromium, twice** (1600px and 1200px: pointerdown on the 文档 grip → pointermove +60 → pointerup on window) and reads the template before and after. The five fixed columns must be unmoved to the pixel and the total must still fit the dialog; the dragged column is judged by a **branch** whose predicate is the `minmax(a,1fr)` written into the DOM (a computed value cannot show it: `1fr` always spends the leftover space, so it never reveals how much the flexible column still has to give). While that column can still give (`a` above its floor — 130 > 120 at 1600px) the dragged column must be **exactly** 60px wider; once it has given everything it has (`a === 120` at 1200px) the requirement becomes *strictly wider, and no wider than the space actually left* — which is `fitDashWidths`' "keep it above each column's min when it does not fit" rendered in a browser. The premise itself is font-dependent: with `fonts-noto-cjk` installed the Chinese pills and buttons are wider, the 1200px case has less room, and handing over 55px instead of 60px is the correct answer — so the assertion is a branch rather than an equals sign (the per-viewport pixel numbers stay pinned in `run-dashview.js` at the pure-function level). Both cases must also show that *after* the drag every `nowrap` column is still ≥ its measured single-line width with `clip === 0` on every button — which is what pins the once-per-render measurement cache (re-measuring on every `pointermove` would be ~240 Range + `getComputedStyle` calls per frame for text that cannot change with width). The page has **no origin**, so `localStorage` access throws — the plugin's guarded `lsRead`/`lsWrite` degrade and the dashboard still renders, which is the private-browsing path tested for free. `LAYOUT_SHOTS=1` writes PNGs for a human, including `shot-dash-1600.png` / `shot-dash-1000.png`; with no Chromium or no `playwright-core` it prints `LAYOUT SKIP` and exits 0, and `run-all.js` renames the step to say it was skipped |

A step passes when it exits 0 **and** prints its own conclusion marker (`FAULT INJECTION E2E OK` and friends) — the fault-injection scripts print failure samples on purpose, so grepping for the word FAIL would read a green run as broken. Each script tears down what it made: `/tmp/wdav-local-test`, `/tmp/wdav-entry-test`, the FTP/SFTP login directories, the test notebook and temporary exports in the SiYuan workspace, and its own remote prefix (`owner-e2e`, `wdav-reg-safenames`, `nginx-test`, `docx-reg`/`wdav-reg-docx`, the upload-error prefix — each asserted gone afterwards). **The IIS leg tears down its own prefix too** (`netglimmer-reg-iis`, deleted leaf-first because IIS `DELETE` is not recursive, then asserted `PROPFIND` 404): no test trace is left on a real server, and the uploaded page is verified by reading it back over HTTP inside the same run rather than by leaving a folder browsable afterwards. Leaving that prefix behind would also compound: the suite uploads from a freshly created notebook document, the ownership guard never deletes (or reuses) a directory whose marker belongs to a different document ID, so every run would add another `WebDAV发布测试-<random suffix>` sibling — the same rule that protects two same-titled documents is a rule the harness has to satisfy. `run-ftpverify.js` deletes the notebook it creates **at the end** of its own run, so the workspace is clean when the suite finishes instead of waiting for the next one. `run-layout.js` touches no server and no kernel — it renders in a throwaway page and only writes `browser/shot-*.png` when `LAYOUT_SHOTS=1` is set. The harness does have a headless Chromium and `run-layout.js` measures with it; the outline/lightbox groups in `run-toc.js` are still stub-driven, so "how it looks" conclusions there remain structural inference rather than rendered fact.

## Known limitations

- Three export formats: HTML (SiYuan), Markdown and Word (.docx) (shape and costs in **Settings → Export format**). Whether a reader can open the upload in a browser depends on the server's MIME configuration — IIS answers 404 for `.md` by default (nginx answers 200 with `application/octet-stream`), while `.docx` answers 200 on both and the browser downloads it or hands it to Word (see **Server notes**).
- **PDF is out of scope, and the reason is that the kernel offers no such path.** SiYuan's kernel export API has no PDF; the only PDF-shaped call is `processPDF`, a pdfcpu post-processor for an *existing* PDF (watermark, bookmarks, embedding assets the links point at) — it does no typesetting, so without PDF going in there is no PDF coming out. On the desktop the "Export → PDF" bytes come from Electron's main-process `printToPDF`: plugin code runs in the renderer, so reaching it takes private IPC (`siyuan-get` / `siyuan-export-pdf`) **and** a real, visible editor window being opened (in remote-kernel mode that path is ignored outright). So this is not "not yet implemented" — there is no reusable PDF capability on the plugin's side of the fence. The workarounds are stated on the settings row itself: export the PDF manually from SiYuan, or upload the Word `.docx` and save it as PDF from Word.
- Word mode depends on the pandoc that ships with SiYuan (this 3.8.6 install carries 3.10.1). When the kernel refuses, the plugin shows the kernel's own wording rather than substituting another typesetter to fake "something Word-shaped" — such an artifact's glyphs, pagination and table of contents would not line up, which is harder to debug than a failure. This mode also needs the **absolute workspace path** the kernel reports, because that is where the temporary artifact has to land: with a remote kernel or a missing path the upload fails on the spot and says why, rather than falling back to a relative path (a relative `savePath` resolves against the kernel's working directory, measured to drop the file into the SiYuan install folder).
- Markdown mode has no "include sub-documents" tier: the kernel's `exportMdContent` accepts a single document id only. The corresponding setting is simply inert while Markdown is selected, and history records are written as "not merged". Word and HTML both honour it for real (Word measured merging the subtree into the same `word/document.xml`).
- Word's `.docx` is uploaded **in full every time**: it is a single file with no reusable runtime, so incremental mode has nothing to do on this path (history `reused` is always 0). Repeated uploads within one run still dedup into one row. The artifact's bytes are not guaranteed to be byte-stable over time (pandoc writes generation timestamps into the package's property files; re-exporting the same document one second later was measured to differ by one byte), so change detection uses the document's content fingerprint rather than a hash of the artifact — "the bytes changed on re-upload" does not mean the content changed.
- Encrypted notebooks cannot be uploaded (the kernel refuses plaintext export).
- SFTP supports password authentication only (no private key / passphrase). Its algorithm set is deliberately narrow, and a server has to meet it: KEX `curve25519-sha256` (also `@libssh.org`) or `ecdh-sha2-nistp256`; ciphers AES-128/192/256-**CTR** (no CBC, and no AEAD — `aes*-gcm@openssh.com` / `chacha20-poly1305` are not offered); MAC `hmac-sha2-256` / `hmac-sha2-512`, **with or without** `-etm@openssh.com`, so servers that predate EtM (OpenSSH < 7.4, several NAS builds) are still reachable; host keys `ssh-ed25519`, `rsa-sha2-256/512`, `ssh-rsa`, `ecdsa-sha2-nistp256`. When nothing intersects, the error names the algorithms the server offered rather than failing silently. The OpenSSH strict-KEX sequence-number reset is applied **only** when the server also advertises `kex-strict-s-v00@openssh.com` — a server without it keeps counting, and resetting anyway would break exactly those older servers. The host key's signature must use the algorithm that was negotiated for it, so a server cannot quietly answer an `rsa-sha2-512` negotiation with a SHA-1/SHA-256 signature. One thing that is *not* implemented: re-keying mid-session. A server that asks to rekey is ignored, its next packet then fails its MAC check, and the transport is reported as lost — which the retry layer handles by reconnecting before the next file (so an aggressive `RekeyInterval` costs a reconnect, not a corrupt upload).
- FTP/SFTP use direct sockets from the desktop Node, so nothing is base64-encoded and no request body passes through the kernel (WebDAV does both, which is why every file has to be read into memory first); the price is that the desktop has to reach the server port directly (corporate proxies: run "Test connection" first).
- Both protocols accept an IPv6 server address, but **FTP transfers are still IPv4-only**: they use `PASV`, whose reply carries four IPv4 octets (`EPSV` is not implemented), so an IPv6-only FTP server will fail when opening a data connection even though the login succeeds. SFTP over IPv6 is covered by a real end-to-end test (`::1` + port 2222).
- The settings-dialog layout is measured for real in headless Chromium against SiYuan's actual CSS — but against a **port** of saplay's `Dialog`/`Setting` behaviour, not SiYuan itself, so another theme or a future host change could differ. Only `run-layout.js` uses a browser; the outline and lightbox groups in `run-toc.js` are still stub-driven, so "how it looks" conclusions there are structural inference rather than rendered fact.
- Change detection compares SiYuan's own block index (block count + last updated); editing the remote files afterwards is invisible to it.
- Ownership detection depends on the `netglimmer-owner-*.json` marker; remove or block it and same-titled documents will overwrite each other again.
- **Delete remote** only deletes the remote path segments stored in that history row. The plugin never rebuilds them from the display URL — FTP/SFTP segments are relative to the login directory and local ones to the base directory, so an address cannot be turned back into segments — a row without them gets no delete button at all, never a delete against a guessed path.
- With server-safe file names on, the name on the server can differ from the one you see in SiYuan (`a+b.png` becomes `a＋b.png`) — page references and Markdown body links are rewritten to match, and names that were already legal are never touched. Two SiYuan-side caveats: an attachment whose name contains `?` is never copied into the export folder at all (the plugin cannot see it, so rename it in SiYuan), and two attachments that collapse onto the same name on the target filesystem still need a manual rename — auto-collision suffixes only apply to the safe-name mapping.
- **No network wait is left unbounded**: every path has a deadline, because an `await` that never returns is the one failure mode no error message can report — the upload simply sits there neither succeeding nor failing until the host is restarted. WebDAV asks the kernel's `forwardProxy` to give up after 90s per request (the kernel's own file read is cut at 60s, as is reading export bytes through the four-step fallback chain); an idle FTP control socket times out at 30s and its data channel gets 120s for a `STOR` flush and 60s to finish a `LIST`/`MLSD` payload; SFTP bounds each phase separately — banner 30s, `INIT` 15s, a request 120s, any awaited reply 20s by default (its socket idle timer is lifted after the banner, since the per-request waits are what actually guard the session). Timeouts are reported as transient, so the retry layer reconnects instead of giving up.
- Cancelling an upload is cooperative: the file currently being uploaded finishes first, so cancelling during one huge transfer waits for it. Interrupting a request mid-flight would leave a truncated asset that the next incremental upload would trust by size.
- The "deleted locally, still on the server" marker comes from SiYuan's block index, so a document sitting in the **trash is not detected as deleted** — measured on the live kernel, trashed documents keep their `blocks` rows. It also inherits the change-detection lag: a document edited seconds ago may still read as unchanged.
- The command-palette and status-bar entries go through the host's `addCommand()` when it exists and are asserted against stand-in hosts in `run-entry.js`, but this machine has no SiYuan frontend — their appearance in a real palette is structural evidence, not an observed screenshot.
- **Dashboard geometry is measured** — the seven columns' floors sum to **862px** under the Chinese dictionary (`156/110/73/95/120/90/218`, measured at 1000px and 800px) and **966px** under the English one (`156/110/82/142/120/90/266` — 协议 73→82 is the header's own label, not a cell), inside a grid whose `clientWidth` measures 1142px at a 1600px viewport, 998px at 1200px, 822px at 1000px and 646px at 800px — so at 1000px the Chinese floors overflow by exactly 40px and at 800px by 216px, and the table is meant to **scroll** there rather than clip, which is a distinction only a layout engine can make. That is why `run-layout.js` measures the dashboard in real Chromium at four viewports and two dictionaries: "the 操作 column is off-screen" and "the buttons wrap" are assertions rather than opinions. One dictionary is not enough: under the English one 结果 truncates to `Remote files de…` and 操作 wraps to three rows, and the Chinese timestamp measures 155px in a single line, which is why 时间's static floor is 156px rather than anything narrower. So the floor of a non-wrapping column is measured from the rendered cells at runtime (`dashColNeeds` + `dashFitCols`, capped at 60 rows), and the same pass measures those headers' own labels too — a `position:absolute` column-width handle that hangs 4px past the cell edge is deliberately ignored there, because that overhang is the handle's job and not truncated text. `run-layout.js` runs **six** cases (1600/1200/1000/800 Chinese + 1600/1000 English) with an explicit "no `nowrap` column may be ellipsised" assertion, which `scrollWidth` cannot provide on plain text. The CSS alternative (`minmax(auto, Wpx)`) does not work here: measured in the same dialog, every track in an over-constrained container collapses to min-content (文档 gets 33px at 800px), because `overflow:hidden` zeroes the automatic minimum anyway. Two things this does **not** cover: it renders the dashboard **tab inside the settings dialog** — the entry the status bar and the command palette use — while the standalone `openDashboard()` dialog/tab is still verified only structurally; and the pixels come from the daylight theme at default font sizes on this machine's Chromium, so a custom theme, a different font or a zoom level yields different numbers (the geometry assertions are written as `clip === 0` / "right edge inside the grid" / "≥ the measured floor" precisely so a reader with a different theme still gets a meaningful pass — while `run-dashview.js`'s `NEED_ZH`/`NEED_EN` tables *are* this machine's numbers and could go red on a wide-font machine without anything actually breaking).
- The dashboard's expanded **path** row is one text line spanning all seven columns, measured in Chromium (`run-layout.js`: spans from `left:0`, sits below its own row, `user-select: all`, no horizontal overflow, collapses again). What remains a structural conclusion is whether a full-width grey text line *reads* as its own row rather than as an eighth column — that is a judgement about appearance, and `LAYOUT_SHOTS=1` saving `browser/shot-dash-1600.png` is the honest way to look at it.
- Local-folder uploads refuse a configured path containing `.` / `..` segments, or one that resolves to a filesystem root, because re-uploading and deleting remote files **recursively delete** inside that folder, and `path.resolve` folds such a path to a shorter root — `/` included. A stored path of that shape is refused on load and the settings field rejects it too, so the mistake surfaces before any file is touched; re-enter it as a plain absolute path.
- The FTP listing verdict is judged against **ten** reproduced server shapes (`run-ftpverify.js`: six `LIST` dialects, three `MLSD` self-entry forms, plus a server that fails on one subdirectory), not against any one person's server — a server nobody can reach cannot be tested, so an unusual dialect may still be unrepresented. If an upload ends with unconfirmed files, the message quotes a 120-character sample of the raw `LIST`/`MLSD` response: read it as "the plugin could not parse your listing", not as "your files are missing", and that sample is what makes the case reportable.
- Deleting dashboard records removes **history rows only** — nothing on the server is touched, and a document whose record was deleted keeps uploading to the same remote path (its ownership marker still says it is yours). Rows for documents still on the server cannot be ticked and have no 删除记录 button; use **Delete remote** first if the goal is to take the folder down. 清空记录 is deliberately *not* guarded — it still clears everything, including rows for live documents, which is why its confirmation names that count: after clearing, the dashboard is not the way back to those remote folders.
